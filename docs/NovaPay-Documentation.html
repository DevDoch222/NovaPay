1. Introduction & Product Overview

NovaPay is a cross-border, multi-currency digital banking platform built for Africa-connected users. It connects local African financial rails (bank transfers, mobile money) with global currencies so people and businesses can hold, convert, send, receive, and spend money with transparent FX.

1.1 Purpose

  • Hold balances in NGN, USD, and EUR
  • Convert currencies with locked, transparent FX quotes
  • Fund wallets and pay out to bank or mobile-money beneficiaries
  • Issue virtual USD cards for online spend
  • Receive inbound ACH/SEPA credits via virtual accounts
  • Pay utility bills and buy airtime
  • Deposit stablecoins and convert 1:1 to/from USD
  • Operate business workspaces with roles and bulk payout approvals

1.2 Target Users

SegmentNeeds
Individuals & freelancers Receive USD/EUR from global clients, convert to NGN, spend on virtual cards
Diaspora senders Move money from UK/EU/US to Africa with clear rates and payout rails
Businesses & organizations Multi-currency ops, team roles, dual-authorization bulk payouts, public API

4. Core Features & User Flows

4.1 Authentication & Onboarding

  1. Welcome carousel introduces the product value propositions.
  2. User enters phone number in E.164 format.
  3. SMS OTP is issued (Redis-backed). Sandbox supports fixed code 000000.
  4. User sets a 4-digit PIN for unlock and transaction authorization.
  5. Optional biometric opt-in (Face ID / Touch ID).

4.2 KYC

Users submit identity documents (e.g. NIN, BVN, Passport). Sandbox can auto-approve submissions, moving users from tier_0 (restricted) to tier_1 (active). Payouts and card issuance require tier_1+; tier_0 single-payout limit is 0.

4.3 Wallets & Double-Entry Ledger

Multi-currency wallets (NGN, USD, EUR). Every financial movement posts balanced debit/credit rows in ledger_entries. Wallet balance is the sum of ledger entries for that wallet. Amounts are stored as bigint minor units (kobo/cents).

4.4 Funding

  1. User selects Add Money on the NGN wallet and enters an amount.
  2. Payment rail: Flutterwave (live NGN rails) or mock/sandbox.
  3. Sandbox: simulate-complete credits the ledger immediately.

4.5 FX Conversion

  1. User requests a quote (e.g. NGN ↔ USD).
  2. Rate = mid-market + configurable margin (basis points).
  3. Quote locks for 60 seconds (TTL countdown in the app).
  4. Booking executes a double-entry transfer between wallets.

4.6 Send & Payouts

Beneficiaries may be bank accounts or mobile money (MTN, Airtel, M-Pesa, etc.). Payouts require PIN authorization and are processed via Flutterwave or mock rails.

4.7 Virtual USD Cards

  • Issue virtual Visa/Mastercard on the USD wallet.
  • Full PANs are never stored — only last4, expiry, and processor references.
  • Controls: freeze, unfreeze, close.
  • Sandbox can simulate authorize → settle against the USD ledger.

4.8 Receive, Bills & Airtime

  • Virtual USD/EUR receiving accounts (routing, IBAN, BIC, bank name).
  • Simulate inbound ACH/SEPA credits in sandbox.
  • Biller catalogs and airtime operators by country, paid with PIN gate.

4.9 Stablecoins & Business

  • Deposit USDC/USDT; convert 1:1 to/from fiat USD.
  • Organizations with roles: owner, admin, approver, member.
  • Bulk payout batches with dual authorization above approval limits.
  • Developer API keys (np_test_...) and webhook registration.

Ledger invariant: every completed financial action must produce balanced debit and credit ledger entries. The wallet balance is derived from the ledger, not stored as a mutable single column.

8.2 Mobile

Set EXPO_PUBLIC_API_URL to the API base URL.

Physical devices cannot use localhost — use your machine’s LAN IP, e.g. http://192.168.x.x:3000.

8.3 Supabase Notes

  • Runtime uses the transaction pooler URL (port 6543).
  • Drizzle migrations use the direct/session URL (port 5432).
  • SSL (sslmode=require) is required.
  • Supabase is used as Postgres hosting only; auth/KYC remain in NestJS.

11. Security & Compliance Notes

  • JWT access tokens are short-lived; refresh tokens rotate over a longer TTL.
  • Session material and PIN unlock are protected on-device via SecureStore and optional biometrics.
  • Card PANs are not persisted in the application database.
  • API keys are stored hashed; only prefixes are returned after creation.
  • Payment and BaaS webhooks are public endpoints and must validate provider signatures/hashes.
  • KYC tiers gate high-risk actions (payouts, card issuance).
  • Idempotency keys on critical money-moving endpoints prevent duplicate posts.
  • Regulatory pathways, custody models, and partner shortlists are documented under docs/phase-0/ (REGULATORY.md, PARTNERS.md).
